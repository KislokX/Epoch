# ADR-0002: Core language — Rust

- Status: Accepted
- Date: 2026-07-22
- Depends on: —
- Related architecture: [[Domain Kernel]], [[Provider Layer]]

## Context
The AIOS Engine owns all business logic — orchestration, providers, tools, integrations, memory, context, events, persistence — and must run headless for future interfaces (CLI, web, mobile, server). Needs reliability, performance, strong typing, safe concurrency (streaming, many providers, background automations).

## Decision
Write the engine in **Rust**.

## Why this is best
- Strong static types enforce the domain kernel (ADR-0006) and capability model (ADR-0005) at compile time — fewer runtime surprises across a 5-year codebase.
- Fearless concurrency for streaming + parallel provider/tool calls.
- No GC pauses; predictable resource use for a long-running desktop process.
- Pairs natively with Tauri (ADR-0001) — one language, no shell/engine FFI seam.
- Trait system fits interface-first design (Provider/Tool/Integration traits).

## Alternatives considered
- **TypeScript/Node** — fastest iteration, weaker guarantees for a system meant to evolve for years; pulls logic toward frontend (violates ADR-0003).
- **Go** — good concurrency + simplicity, weaker type expressiveness for the domain kernel; less ideal Tauri fit.
- **C#/.NET** — capable, but heavier runtime and weaker cross-platform desktop story here.

## Consequences
- Slower raw iteration than scripting — mitigated by making agent/prompt/workflow definitions **data-driven and hot-reloadable** (pending Definition Registry ADR), so behavior changes without recompiling.
- Higher contributor bar; offset by documentation-first workflow.

## Assumptions
- Definition-as-data keeps day-to-day iteration fast despite a compiled core.

## Risks
- Compile times / iteration friction. *Mitigation:* data-driven definitions; modular crates.

## Open questions
- Crate/workspace layout (one engine crate vs. many) — decide at scaffold time.
